### Decision of the orchestrator (2026-11-17)

Decision for T4 (the parse status of sqll and sqlfluff on each corpus
file is recorded, and each difference has a row) of S4 (parser parity:
sqll passes 100% of the dialect parse fixtures with an exact tree
match). Decided on 2026-11-17 by the orchestrator under the standing
delegation (CONSTITUTION.md, section 5). This decision does not need the
human owner.

- Decision: keep the full profile, the 2 tools (sqll and sqlfluff), and
  the corpus layer of sqll. Do not make the run shorter. Do the run as 24
  shards of one run (`run --shard K/24`). Each shard is one bounded step
  that keeps its result. Then join the shards with the `merge` command of
  the corpus harness of S9 (external corpus: large, complex SQL files
  from public sources, with their source and license; the report shows
  parse success and speed for each file, for each tool), with an
  `--expect` file `{"shards": 24}`, and run `check` on the merged report.
  The CI job `corpus-full` uses the same merge tool. Its check fails
  closed.
- Data: (1) `results/S9/baseline.json` has 164 files in the full
  profile. The sum of the sqlfluff wall time is 2722 s (about 45 min).
  The largest files take up to 216 s each (warmup and timed runs; policy
  `full`: `max_runs` 5, `budget_s` 10, `timeout_s` 1200). One full run
  does not fit in one turn: the earlier author run stopped after 5 of 164
  files, with no report. (2) `run --shard K/N` selects the files with
  index i where i % N + 1 == K. `merge` fails closed if a shard is
  missing or repeated, if the shard counts are not the same, or if 2
  reports have a different `sqlfluff_ref`, harness commit, profile,
  policy, manifest, scope, or tool record. It also does the schema check
  and the completeness check on the merged report. (3) Estimated longest
  shard from the baseline order (sqlfluff only): 9.0 min with 6 shards,
  5.8 min with 12 shards, 4.2 min with 24 shards. (4) CI cannot do this
  run: `corpus-full` uses the default tools, and sqll is in `LATER`. A
  change to that file belongs to the corpus track (T12 and T13 of S9, not
  started), and design record section 4 does not let this track change
  it.
- Rules: all 24 shards on one clean commit of `claude/s4`, with no commit
  between shards; the sqll binary is built once; each shard is one
  command with the machine lock (PROCESS.md, "Tracks", rule 7), with its
  report in `out/s4-corpus/shard-K-of-24.json`; a shard report is never
  edited, and a shard is not run again if its report exists; if the
  merge fails, all 24 shards run again on one commit; no file is removed
  from the scope. Timing is information only for T4, not a speed claim
  for G3 (speed: each command, start time included, is as fast as
  reasonably possible and has a benchmark that measures sqlfluff, sqruff,
  and sqll on the same input; sqll is faster than sqlfluff on each
  benchmark, not slower than sqruff on any benchmark, and faster than
  sqruff on the total of all benchmarks; a change that makes a benchmark
  slower gives the reason; correctness is more important than speed: do
  not make a result wrong to make it fast).
- Reason: the decision gives the same data as one full run. Each file
  and each tool is in the report, with the same profile and settings, and
  a merge that fails closed joins the shards. It does not weaken G4
  (verification first: each behavior has an automated test; tests come
  from external sources; external test data has its source, version, and
  license, and does not change to make a test pass; one command runs all
  tests and benchmarks, and the output is machine-readable; each known
  failure is in a list) or an exit rule. It uses only existing tools, so
  no file of the corpus track changes.
